### 2.1 Feature policy (explicit, per root)

egui 0.37 has **no default `default_fonts`** (`egui/Cargo.toml`: `default_fonts` off by default),
and 0.37 moved the monochrome emoji faces out of `default_fonts` into
`monochrome_emoji_fonts` (`epaint/src/text/font_definitions.rs:127-183` inserts
`NotoEmoji-Regular`/`emoji-icon-font` only under that cfg). eframe 0.37's default feature set
includes `clipboard`, and its `egui-winit` dependency is `default-features = false`, so an app that
turns eframe defaults off must add `clipboard` itself (`eframe/Cargo.toml:142-144`;
`egui-winit/Cargo.toml:44-46`, `clipboard.rs`).

| Root | Features after migration | Why |

## 4. Concrete source design

### 4.1 How the hosts actually call the app

Verified statically at `a4f9a17f` (and unchanged in shape from 0.36.2):

- **Native** (`eframe/src/native/epi_integration.rs`): `App::logic` and `App::ui` are both called
  **inside** the `Context::run_ui` closure, so both run **once per layout pass** (a discard can
  produce more than one). `raw_input_hook` is called once per host `update`, before `run_ui` (and
  before `run_logic` on a hidden logic-only update), not per pass.
- **Web** (`eframe/src/web/app_runner.rs`): the same — `logic` then `ui` inside the `run_ui`
  closure, per pass.
- **Headless** (`crates/ui-egui/src/headless.rs:320-325`): `Headless::step` calls
  `HeadlessView::run(raw, |ui| { app.logic(ui.ctx()); app.ui(ui) })`, which is
  `ctx.run_ui(raw, …)`; again per pass.
- **Hidden**: the integration calls `Context::run_logic`, which updates only window/focus state;
  events, input time and layout remain from the last UI pass.
- After a completed `run_ui`, `current_pass_index()` is **0** (`ContextImpl::end_pass` takes the
  output with `mem::take`; `run_dyn` restores the count only immediately before the next pass, and
  `run_logic` does not restore an old index). During a second pass it is 1, 2, ….
- `ViewportInfo::visible()` derives from minimized/occluded and is `None` when unknown. **A hidden
  window can still run a full UI pass**: `egui-winit`'s `ActionRequested::Screenshot` and
  `PaintWhileHidden` both report `wants_paint()`, and eframe treats that as `is_visible` for the
  pass (`wgpu_integration.rs:687-704`, `glow_integration.rs:680-693`). In that forced paint
  `visible()` still reports `Some(false)`.

Consequences: (a) `visible()` and fresh egui time are **not** a way to tell UI work from logic work;
(b) `current_pass_index() == 0` is a valid *known-UI-boundary* test for "first pass of this
`run_ui`", and it is also true during `run_logic`, so a hidden tick is never suppressed by it; (c) a
second pass has empty input events (`InputState::begin_pass` replaces events with `new.events`), so
event-driven code cannot run twice, while time/state-gated code can.

### 4.2 The tick contract (no `TickPhase`, no visibility classifier)

R1's `TickPhase { First, Later, Hidden }` and its time/visibility classification are **removed**.
They had no defined first-call, `visible() == None` or forced-hidden-paint branch, and their
stale-`current_pass_index` rationale was false. The replacement is a small, explicit split with a
monotonic clock and consumed queues:

```rust
impl LightcraftApp {
    /// Background/queue work. Called before layout on every host pass (native and web
    /// inside `run_ui`, headless in `Headless::step`) and from `Context::run_logic`
    /// while hidden. It may read `ctx.input(|i| i.viewport())` and `i.raw.focused` only
    /// (those `RawInput` fields are refreshed by `run_logic`; `i.focused` and `i.time`
    /// are not). Never events, dropped files or keys.
    pub fn logic(&mut self, ctx: &egui::Context) {
        i18n::set_language(self.ui.language);
        panels::library_problem::logic(self);
        panels::notices::logic(self);
        if ctx.input(|i| i.viewport().close_requested()) && !panels::notices::may_close(self) {
            ctx.send_viewport_cmd(egui::ViewportCommand::CancelClose);
        }
        let now = self.tick_now();                  // monotonic; see 4.3
        self.drain_control(ctx);                    // control_rx.take() + try_recv: consumed once
        self.renderer.poll(ctx, &mut self.session);
        merge::poll(self, ctx);
        import::poll_scan(self, ctx);
        sync::poll(self, ctx);
        sync::poll_run(self, ctx);
        tasks::poll(self, ctx);
        import::tick(self, ctx, now);               // time-gated; second pass is a no-op
        lightroom_import::tick(self, ctx, now);
        recheck::tick(self, now);
        self.slideshow_tick(ctx, now);
        self.auto_import(ctx, now);
        self.retry_sidecars(ctx, now);
        self.scan_devices(ctx, now);
        self.preview_build_status(ctx, now);
        self.save_status(ctx, now);
        self.pump_background_queues(ctx, now);      // faces/denoise/model/focus worker results
        self.collect_captures(ctx);                 // completion slot: take once
        self.issue_captures(ctx, now);              // admit/issue; deadlines use `now`
        self.session.persist_if_dirty();
        if !self.synthetic.is_empty() {
            ctx.request_repaint();                  // visible gesture steps
        }
        if self.needs_paint_while_hidden(ctx) {     // pending gesture, queued capture or settle
            ctx.send_viewport_cmd(egui::ViewportCommand::RequestPaintWhileHidden);
        }
    }

    /// Input and once-per-layout-frame work: the known UI phase.
    fn ui_pass(&mut self, ui: &mut egui::Ui) {
        let ctx = ui.ctx().clone();
        if ctx.current_pass_index() == 0 {
            self.take_dropped_files();              // from the queue filled once by raw_input_hook
            self.pump_ui_input(&ctx);               // the input-reading halves of faces/denoise
            self.update_perf(&ctx);
        }
        self.sync_theme(&ctx);
        self.apply_settings(&ctx);
        if self.fonts_ready {
            shortcuts::handle(self, &ctx);           // fresh events only
        }
        self.check_external_editor(&ctx);
        self.resolve_pending_gestures();             // after this pass's layout, see 4.4/4.5
    }
}
```

Rules that the implementation and its tests must keep:

1. **One consumer per queue.** `drain_control` takes `control_rx` out, drains with `try_recv`,
   puts it back; replies are sent exactly once. The screenshot slot is `take`n once. Worker results
   carry a generation id and are applied once. There is no "run the queue again" path.
2. **`current_pass_index() == 0` guards once-per-host-frame work**: dropped-file consumption,
   input-reading halves (`pump_ui_input`) and perf update, and `import::tick`'s batch commit. A
   hidden `run_logic` also reports index 0, so the same gate lets import work advance on a hidden
   tick. It is *not* the gate for the other background timers: Lightroom import, slideshow,
   auto-import, sidecar retry, device scan, recheck, toasts and autosave live in `logic` behind
   monotonic deadlines. A wall-clock gate cannot substitute for the pass index: a discarded first
   pass that takes longer than the throttle would re-run it inside the same host frame. Where an
   operation needs "how many frames have actually run", use `Context::cumulative_frame_nr()` (one
   per `run_ui`), not the pass index and not `cumulative_pass_nr`.
3. **Input lives in the UI phase.** `shortcuts::handle`, dropped-file handling and the
   external-editor focus check move out of `logic_inner` into `ui_pass`. A hidden `run_logic` tick
   can no longer re-read the last pass's `dropped_files` (today it would spawn the same import
   again) and cannot consume a queued key.
4. **Only refreshed window state is safe in `logic`.** `run_logic` refreshes
   `RawInput::viewports`/`RawInput::focused` only; `InputState::focused`, `InputState::time` and
   events stay from the last pass. Read `i.viewport()`/`i.raw.focused` in `logic`, and `i.focused`/
   `i.time` only in the UI phase.
5. **No freshness inference from visibility.** `Some(false)` + a running `App::ui` is a normal forced
   paint (pending screenshot or `RequestPaintWhileHidden`); `None` is normal for headless and
   `RawInput::default()`. Visibility must not be used to tell UI work from logic work. It *is*
   used deliberately for user-facing pacing: a minimized/occluded (`Some(false)`) slideshow pauses
   instead of advancing and requesting full-size slide renders, and resumes with its remaining
   time on unhide (P2.5 in the post-port review).
6. **First call / first frame.** `tick_now` is initialised at construction and every timer is an
   `Option`/deadline comparison that is true on the first tick, so `Headless::step` at time `0.0`
   and `ctx.run_ui(RawInput::default(), …)` (whose input time is `prev + predicted_dt`, not 0) both
   run their first logic work. Add explicit tests for both, plus `visible() == None` and a forced
   hidden paint (§6.1).
7. **No `will_discard` prediction.** A later widget may request a discard after logic has already
   run; correctness comes from one-consumer queues and idempotent side effects, not from guessing.

### 4.3 Hidden-time accounting: one monotonic clock, painting stays egui time

`run_logic` leaves `ctx.input(i.time)` frozen, so any timer read from it in `logic` is stale.
Introduce an app clock and use it for everything that must progress while hidden:

```rust
/// Seconds since the app was constructed. Monotonic (`web_time::Instant`): never goes
/// backwards, even when the window is restored after hours hidden.
fn tick_now(&self) -> f64;
```

- Use `tick_now` for: `import::tick` (additionally gated by `current_pass_index() == 0` so a
  discarded pass cannot commit twice), `lightroom_import::tick`, `recheck`, slideshow playback
  (`panels/slideshow.rs:157-183`; auto-paused while `ViewportInfo::visible() == Some(false)`),
  auto-import (`lib.rs:1154-1187`), sidecar retry
  (`lib.rs:1190-1214`), device scan, screen-profile refresh (`lib.rs:1316-1322`),
  denoise/faces/focus/model timers, autosave/prefs cadence, capture settle/fallback/timeout
  deadlines, and **toast expiry**. Each stores a next deadline and advances it only when
  `now >= deadline`, so a second pass in the same host frame is a no-op.
- Toasts: store the deadline as a monotonic app-clock value; `save_status` (`lib.rs:785-808`),
  `preview_build_status` (`lib.rs:756-781`) and `panels::toast` (`panels/mod.rs:80`) read
  `tick_now`, not `ctx.input(i.time)`. A hidden toast then keeps its remaining time instead of
  expiring the instant the window is shown.
- Keep egui time for painting, animation, gestures and widget interaction (all of which only run in
  the UI phase).
- The web host's `safety::take_notices` (`apps/lightcraft-web/src/web.rs:654-656`) runs in `logic`
  and today uses `ctx.input(|i| i.time)`; give it the same monotonic deadline.
- `Headless` exposes its simulated time through the same clock (a test hook; the current
  `Headless::time` starts at `0.0`).

### 4.4 Duplicate-work inventory (narrowed)

The second pass has **empty events**, so `shortcuts::handle`, dropped-file handling and
`collect_screenshots`-style event scans cannot run twice from one gesture. The real duplicate
candidates are state/time-gated calls that `logic` runs on every pass (a monotonic deadline makes
the second pass in a host frame a no-op), and one call that is literally duplicated today:

- `panels::faces::pump` is called twice in one pass (`lib.rs:1139` and `:1228`);
- `import::tick`, `lightroom_import::tick`, slideshow timers, auto-import, sidecar retry, device
  scan, recheck and the toast/status updates are time-gated, so a slow second pass could fire them
  again;
- `WebApp::run_inbox` and `load_originals` drain queues on every call (correct — they are consumed
  queues), while `import_dropped` re-reads `raw.dropped_files` on every call and must not run in a
  hidden tick or a later pass; it moves to the UI phase and consumes an app queue filled once in
  `raw_input_hook`.
- `panels::denoise::pump` (`denoise.rs:45-52`) and `panels::faces::pump` (`faces.rs:705-712`)
  read `ctx.input` keys/pointer/`i.time` to pace background work. Split each into
  `pump_background` (download/index worker results, monotonic deadlines — safe in `logic`, including
  hidden) and `pump_ui_input` (fresh key/pointer activity and its timestamp — UI phase only). A
  hidden tick must never pace work from the previous pass's pointer state.
- `WebApp::save` stays guarded by its own `last_save` deadline, now on the monotonic clock.

There is no evidence that event-driven handlers need multi-pass guards, so do not add them.

### 4.5 Control gestures while hidden (geometry, paint requests, one reply)

Today `ui.clickWidget`/`ui.dragWidget`/`ui.hoverWidget` read `app.widgets` from the previous pass,
`ui.pointer` maps through the previous `app.image_rect`, and `raw_input_hook` injects one pointer
event (or one up-to-release key run) per host frame. A hidden request can therefore click stale
geometry, and a multi-event gesture can stall after one `RequestPaintWhileHidden`.

New contract:

- **Geometry is resolved only after a fresh layout.** Control requests that need geometry are
  admitted into a `pending_gestures` list with their original params and `admitted_epoch =
  layout_epoch`; `layout_epoch` (a monotonic counter, not a hash) is incremented at the **end** of
  every completed `App::ui` pass. A request resolves, using that pass's `app.widgets`/
  `app.image_rect`, at the end of the first pass where `layout_epoch > admitted_epoch`. If no UI
  pass has happened since admission, the request stays pending and the app sends `ViewportCommand::RequestPaintWhileHidden` (when
  `ctx.input(|i| i.viewport().visible()) != Some(true)`) so the next host iteration paints.
  If the session has never laid out a UI, reply with an explicit "no current UI frame" error at the
  deadline instead of inventing geometry.
- **One unapplied step survives repeated hidden ticks.** `raw_input_hook` is called before
  `run_ui` and before `run_logic` (`epi_integration.rs:338-365,413-430`), so a hidden logic-only tick
  can invoke it. The hook injects at most one queued gesture step and marks it in flight; it must
  not inject another step until a completed UI pass (tracked by a UI-pass counter incremented at the
  end of `ui_pass`, never by `visible()`) has consumed that step. The step remains in eframe's
  `pending_raw_input` across hidden ticks unchanged. This prevents two hidden ticks from batching a
  press and release into one later pass, and preserves key-press-through-release semantics.
- **Each gesture step keeps painting.** While `synthetic` is non-empty (a drag has many moves; a
  click is move+down+up) the app sends `RequestPaintWhileHidden` again after each step is consumed,
  so hidden gestures complete instead of waiting for the user. The hook still injects only one
  pointer move or one key sequence per host update.
- **Exactly one reply, after delivery.** The reply is deferred until the gesture's final synthetic
  event has been injected into a UI pass (a `pending_gesture.delivered` flag set at the end of that
  pass), or until the monotonic deadline, when it replies with an error. A dropped sender gets no
  reply; a canceled/closed request is removed before replying. This makes a successful reply mean
  "the UI saw the gesture", not "events were queued".
- `ui.key`, `ui.text` and `ui.scroll` need no geometry but do need a UI pass to be consumed
  (`ctx.request_repaint()` alone only runs `run_logic` while hidden), so they follow the same
  request-paint/one-reply pattern.
- `ui.screenshot` is **not** a gesture, but it has two phases. Once the
  `ViewportCommand::Screenshot` is processed, `ActionRequested::Screenshot::wants_paint()` makes the
  integration paint a hidden window. A capture that is merely queued or settling in `logic` has not
  reached that phase: while hidden it needs `RequestPaintWhileHidden` from `logic` (the same
  predicate as pending gestures) to reach a UI pass that issues the command. Test both the
  issued-command forced paint and the queued/settling hidden case; do not expect a missing
  issued-command paint to fail.

**Implementation amendment (2026-10-24, before code).** The app owns the queue described above:

- `layout_epoch` is a `u64` incremented once at the end of every **completed, nondiscarded**
  `App::ui` pass (the same place `ui_passes` advances). `PendingGesture` records `admitted_epoch`,
  an admission-time `GestureFrame` (view, active photo, library generation, dialog discriminant,
  left/right/presets/filmstrip switches), a monotonic `deadline_ms`, the original method and params,
  its reply sender, and the computed result once resolved. At most 32 may be pending; a 33rd is
  refused by a normal control error. The deadline is 5 s from admission (`GESTURE_TIMEOUT_MS`).
- `ui.clickWidget`, `ui.dragWidget`, `ui.hoverWidget`, `ui.pointer`, `ui.move`, `ui.click`,
  `ui.drag`, `ui.key`, `ui.text`, `ui.scroll`, `ui.zoom` and `ui.clipboard` are queued. Their
  existing parsing/event construction moves to one `control::gesture_events(&mut app, ctx, method,
  params)` function, called **only after** a completed layout newer than admission. Widget ids and
  `app.image_rect` therefore always come from that fresh pass, never the previous registry. A
  widget that no longer exists, a missing image rect, an invalid key/unit/phase or a removed text
  focus answers once with the existing error, after that fresh pass (not at admission).
- Resolution happens in `finish_ui_pass` after `layout_epoch += 1`. Before computing geometry the
  request's `GestureFrame` must still equal the current frame. A view, active-document, library,
  dialog or panel-layout change between admission and resolution cancels the request with one
  error instead of retargeting the new UI. The per-frame `layout_epoch` advance that makes the
  layout fresh is expected and is not itself a cancellation. A request that never sees a completed
  UI pass (hidden with no paint) answers `no completed UI frame` at its deadline.
- Resolution appends the gesture's synthetic events and marks the request resolved. It is **not**
  answered yet. The reply is sent when `app.synthetic` is empty after a completed nondiscarded pass
  (for a zero-event action such as a clipboard paste request, after the next completed pass), so
  `{"ok": true}` means the UI consumed the last event. A hidden run keeps sending
  `RequestPaintWhileHidden` while any gesture is unresolved or resolved-but-undelivered; a visible
  run keeps `request_repaint`.
- The queue is fail-closed on timeout: the request is removed, its reply error is sent once, and
  queued synthetic input is cleared so a late event cannot click after an error. This can discard
  another queued gesture's still-undelivered events; those requests are answered with their own
  timeout/cancel error rather than being retargeted. The queue is intentionally not a general
  scheduler: immediate commands (`engine.execute`, `ui.set`, `ui.inspect`, `ui.resize`,
  `ui.zoomFactor`, screenshot admission) keep their current direct semantics.
- Limit: the `GestureFrame` cancellation covers the navigation/modal/panel state that can change the
  meaning of an automation id. It cannot prove that a widget with the same id kept the same
  semantic target across an arbitrary catalog refresh inside the same frame; the fresh layout and
  the explicit view/document snapshot are the contract, not a per-widget identity guarantee.

### 4.6 Screenshot capture: the shared CL-2F weak completion slot

Anchors: `crates/ui-egui/src/lib.rs:909-987` (`drain_control`, `issue_screenshots`),
`:1034-1057` (`collect_screenshots`), `:1502-1525` (`PendingShot`), `control.rs:432-439`,
`headless.rs:133-174` and `:310-349`.

craft-libs selects one narrow completion-slot helper (`crates/ui/src/capture.rs`, CL-2) after the
DesignCraft and GridCraft adapters, then freezes the public API (CL-2F). LightCraft is one of the
craft-ui capture consumers and **adopts that helper** rather than keeping the local
`mpsc::Receiver`/token design; names and signatures come from the reviewed CL-2F revision, not from
this document. Every creative capture consumer adopts the CL-2F completion contract:
`craft-ui-consumers-exact.json` shows eleven apps whose TOML declares `craft-ui` (LightCraft among
them). All eleven require craft-libs **CL-1** and the frozen **CL-2F** API in the same atomic
dependency stage as egui/winit; only DesignCraft/GridCraft pilot the provisional CL-2 API, and their
adapters land before CL-2F freezes it. DeckCraft, FigCraft and ArtCraft Native use
contract-compatible local adapters without adding the crate, and all fourteen capture consumers
remain in scope. (The earlier "thirteen craft-ui consumers" wording was wrong; it is not repeated
here.)

LightCraft's adapter (app-owned policy, shared completion transport):

- **One record per admitted request**, owned by the app: monotonic request id, path, reply sender,
  `headless`, admission/deadlines (settle ≥3 painted frames and ≥120 ms; compositor fallback 2 s;
  hard timeout after admission), frames waited, reserved bytes, and a snapshot of capture-time
  geometry (`content_rect`, `viewport_pixels`, `pixels_per_point`, UI zoom). "Frames" means host
  frames (`Context::cumulative_frame_nr()`, incremented once per `run_ui`), not passes, so a
  multipass frame counts once and does not make a screenshot fire early. Take the geometry from the
  refreshed viewport information (`i.viewport().inner_rect`, `native_pixels_per_point`) when present,
  otherwise from the last laid-out content rect; a hidden window has no new layout, so both are the
  last known size, and the reserved bytes are revalidated against the returned image.
- **Issue** with a callback holding **only** a `Weak` reference to the app-owned completion slot;
  the app owns the strong slot and a live, owner-specific completion waker. The callback receives
  pixels only: no `Context` clone, no `&mut LightCraftApp`, no encoding, file I/O or command
  execution. On completion it locks the slot, stores the image, unlocks, and only then invokes the
  waker; it never wakes itself from inside the lock or re-enters the app. A late or canceled
  callback finds no upgradable slot and is a no-op. The renderer owns the callback until it fires,
  so this is not a `Context` reference cycle; `Weak` lets cancel/close drop the app state and makes
  a late result harmless. A pending capture keeps `request_repaint_after(16 ms)`, which also runs
  `run_logic` on a hidden native window, so the woken poll collects completion while hidden.
- **Completion**: take the slot once, release the byte reservation with a checked subtraction, and
  bind the image to the **issuance** UI geometry, DPI and zoom epoch. Any change to logical viewport
  size, surface pixels, `pixels_per_point` or UI zoom between issue and save cancels and retries (or
  replies with an error at the deadline) — even if the geometry changes back to the original values
  before the image arrives. Never combine old pixels with new geometry, and never accept an image
  merely because its dimensions happen to match. Reject an image larger than the reservation and
  release its bytes, then encode/write on the UI thread and reply exactly once. Derive the effective
  scale from the returned image dimensions and the recorded logical viewport (E2 surface fitting can
  shrink the image); record that with the result. Additive result fields (`scale`, `viewport`) are
  optional and backward compatible.
- **Admission is bounded before issue** using the shared capture defaults: at most **4**
  outstanding requests, at most **128 MiB** per image, and at most **256 MiB** aggregate reserved
  in-flight/completed bytes. App-specific caps may be stricter, never looser. Require
  `0 < width,height <= max_texture_side` (16 384 at inspection), compute the reservation with
  checked `width * height * 4` before issuing, and revalidate it after any geometry/DPI/zoom change
  before issue. Reserve the **worst surface the request can produce** — the full logical viewport ×
  `pixels_per_point` × UI zoom × 4 bytes — not the smaller E2-fitted size, and keep
  completed-but-not-yet-drained images counted until they are taken (in-flight and completed bytes
  are both checked before issue). The renderer's own readback allocation is accounted separately in
  peak RSS; a post-callback size check alone does not bound peak memory.
- **Cancel/close/drop/timeout**: remove the record first; the late callback's `upgrade()` fails and
  the image is dropped with no second reply and no panic. On shutdown all reservations return to
  zero. Tests assert retained bytes reach zero after drain/cancel.

**Implementation amendment (2026-10-24, before code): path identity at write time.** Admission pins
the destination as a `WriteTarget` owned by the app record:
`WriteTargetState::Absent` (the directory entry did not exist) or `Existing(FileIdentity)` (device
and inode on Unix; canonical path, length and creation time on Windows, whose volume/file-index
metadata is still unstable; canonical/len/mtime elsewhere; taken from `symlink_metadata` so a link
replacement is a different entry). Admission
still runs the library `OriginalGuard`. Immediately before encoding/writing, **both** the renderer
callback completion and the CPU/headless fallback call `revalidate_write_target`:
- an `Absent` target must still be absent; a file created after admission (ordinary file, imported
  original, hard link or symlink) is refused, never replaced;
- an `Existing` target must still be the same directory entry and must pass `OriginalGuard` again
  against the current catalog, so a photo imported at that path while the capture was queued is
  refused;
- an existing allowed screenshot destination keeps its normal overwrite behavior.
An absent destination is written through the new host `write_new` service
(`lightcraft_engine::export::write_file_new` → `safe_file::write_new`): it prepares a complete temp
file and publishes it with `create_new`/hard-link semantics, so the final TOCTOU window cannot
replace a file that appeared. The bounded temp file is encoded bytes only. An existing destination
uses the existing atomic writer after revalidation. Failure to configure `write_new` for an absent
target is an explicit error (fail closed), not a fallback to the destructive writer. Limits: an
existing destination can still be swapped by another process in the instant between revalidation
and the atomic rename; closing that would require an OS conditional-replace primitive. The lexical parent is now re-resolved before completion and compared with its admitted
canonical parent; a retargeted directory symlink is refused. The deterministic tests cover an absent
path that becomes an ordinary file, an absent path that becomes a catalogued original through a
hard link, an existing original/symlink refused at admission, an existing allowed overwrite, and an
existing target replaced by a new entry while queued, and a parent symlink retargeted between
admission and completion (neither destination receives a screenshot).
- **Both headless entry points change**: `HeadlessView::run` retains `ViewportCommand::Screenshot`
  callbacks and calls `callback.complete(Arc::new(self.paint()))` after the pass; `Headless::step`
  deletes its `ViewportCommand::Screenshot(user_data)` arm (it no longer compiles in 0.37) and no
  longer pushes `Event::Screenshot`. Completion happens exactly once, in the headless host.
- `headless_host` remains the CLI/headless flag; `WebApp` does not set it, and the web path has no
  control server (§4.11, §8).
- Boundary: the shared piece is only the completion slot. Request ids, paths, settle delays,
  deadlines, reply schema and `Services.write/png` stay LightCraft policy in
  `lightcraft-ui-egui`; do not grow a generic screenshot framework in craft-ui for LightCraft.

### 4.7 Panels, IDs and docking

Anchors: `crates/ui-egui/src/panels.rs:52-77` (`resizable_side`),
`panels/bottombar.rs:24,371`, `panels/strip.rs:19`, `panels/topbar.rs:57`,
`panels/library_problem.rs:169`, `crates/ui-egui/src/docking.rs:430`, `shortcuts.rs:339`.

`resizable_side` must pass the **original salt source** to the panel and derive the persisted key
from the same parent scope:

```rust
// `Panel::new` stores `IdSalt::new(id)`; `Panel::id` is `parent_ui.scope_id().with_salt(store)`.
// `Id::with(salt)` is exactly `with_salt(IdSalt::new(salt))`, so this is the panel's real key.
let pid = ui.scope_id().with_salt(egui::IdSalt::new(id));
ui.ctx().data_mut(|d| d.remove::<egui::containers::panel::PanelState>(pid));
let panel = if left { egui::Panel::left(id) } else { egui::Panel::right(id) };
// ... show ...
if !ui.ctx().is_being_dragged(pid.with("__resize")) {
    return None;
}
```

Why this exact form: `Panel::left(salt)` with an already-built `IdSalt` would store

### 4.9 Text input, IME, RTL, clipboard and PRIMARY

- `Event::MouseWheel` initializers in `control.rs`, `headless.rs`, examples and tests get
  `source: egui::MouseWheelSource::Unknown`; `ui.scroll` accepts optional
  `"source": "unknown"|"wheel"|"trackpad"|"momentum"`, `"unit": "point"|"line"|"page"` and
  `"phase": "start"|"move"|"end"|"cancel"`. Omitted values keep the pre-0.37 request meaning:
  `Unknown`, `Point`, `Move`. Every value is validated before an event is queued; an invalid value
  is a control error and changes nothing. This lets tests drive the grid/filmstrip
  `MouseWheelUnit::Line` path and trackpad/momentum `TouchPhase::Start`/`End` cycles, which the
  point/move-only API could not represent. `docs/control-protocol.md` documents the three optional
  keys. Unit tests assert wheel/line/start, trackpad/point/end and the backward-compatible omitted
  defaults.
- `raw_input_hook` keeps the §4.5 one-step-per-UI-pass contract; a logic-only tick must not drain
  another step. `Event::PasteImage` and `MiddleClickPaste` are not app shortcuts — `keymap.rs`'s
  recorder ignores them.
- **E21b/P7b is a new blocking prerequisite, not existing E21 behaviour.** Candidate egui-winit
  never calls `WindowExtWayland::set_ime_surrounding_text`, and `egui::IMEOutput` carries no logical
  text. The complete shared contract is in egui plan P7b and `ime-surrounding-gap.md`; LightCraft
  must take all of it, not a weaker subset:
  - owner/context-generation identity is present even when surrounding text is **Unavailable**. An
    available **empty** document is distinct from unavailable and is sent explicitly as an empty
    payload, not omitted;
  - changing owner or available/unavailable support clears the cached text and commits the
    protocol's disable/enable boundary (not merely empty text); same-owner ordinary updates preserve
    composition; the old preedit is canceled, not inserted into the new editor; there is no
    cross-window bleed;
  - the final completed pass's descriptor, including an authoritative `None`, is what
    `PlatformOutput::append` uses (replace `ime.or(self.ime)`); descriptor, owner and payload are
    one atomic value;
  - focus epochs and protocol serials are tracked separately: a current-epoch `done` with a
    mismatched serial applies incoming edits **once** and defers outgoing state until a matching
    serial; an obsolete owner/epoch invalidates its pending batch. Never drop valid incoming edits;
  - the payload is bounded (≤4000 UTF-8 bytes, valid boundaries, preedit excluded, byte
    cursor/anchor, explicit unavailable when a selection cannot fit) and the **new** payload path
    allocates no full-document clone. Existing `TextEdit` change-detection/undo clones are a
    separately measured baseline, not rewritten here;
  - built-in `TextEdit` produces the payload after delete/commit/cursor updates (logical model
    text, preedit removed, byte indices remapped) and the Wayland adapter sends it through W27.
  LightCraft has no custom `IMEOutput` producer: its `TextField` wraps the built-in `TextEdit` and
  other panels use `TextEdit` directly, so it **inherits** the producer and must test the inherited
  behaviour. The family's custom editors (FilmCraft `panels/graphics.rs` and the others in
  `ime-surrounding-gap.md`) need real logical-model/preedit/UTF-8-index adapters before family
  acceptance; `None` placeholders are not a completed port.
- IME tests: outgoing surrounding text immediately after deletion-only and delete+commit batches;
  preedit excluded; reversed selection; supplementary/combining/RTL text; cursor movement; a very
  long line and an over-limit selection (explicit unavailable, not a truncated claim); available
  empty vs unavailable; field and two-window switches; owner transition with committed
  disable/enable; password/no-IME clears; focus loss/reset/late serial; a current-epoch serial
  mismatch applying incoming edits once while outgoing waits, and a stale-epoch batch discarded;
  multi-pass final output including authoritative `None`. One native Wayland
  Vietnamese/predictive trace checks the outgoing protocol plus editor text and one undo
  transaction.
- Bidi: a mixed Arabic/Hebrew + Latin filename and keyword stays logical in catalog/XMP while
  painted text/caret/selection follow visual order, with no double bidi and no tofu when the
  craft-fonts face is present. The UI stays LTR; do not enable `Style::right_to_left`.
- Clipboard: native `clipboard` feature (§2.1), normal cut/copy/paste through `ui.clipboard`, the
  text-field menu, and PRIMARY middle-click. E4 and **W15P** are one compatibility unit: the
  inspected E4 uses an arboard fallback and does not provide the required winit-owned per-seat
  PRIMARY path. Require the complete P8/W15P revision: PRIMARY has its own protocol object on the
  existing connection/event queue (SCTK 0.19.2 `PrimarySelectionManagerState`/device/source/offer;
  never a second regular `wl_data_device`), and accepts a fresh trigger serial from **either a
  pointer press or keyboard focus** on the focused seat — do not impose a keyboard-only rule.
  Selection claims are synchronous while the trigger serial is fresh; serving and transfer are
  asynchronous. P2b replaces blocking reads/writes on the egui event path with caller-owned bounded
  async transfer handles: a total **2 s** deadline (not a per-`WouldBlock` poll timeout), a
  **16 MiB** byte cap, at most **four** read workers and **two** writer workers with queue depth
  **8**, an owner-specific live completion waker, and cancellation/discard of stale results when
  focus, target, owner or input generation changes. Test on wlroots/KWin/Mutter: keyboard- and
  pointer-triggered selection with valid per-seat serials, middle-click paste, password exclusion,
  no reclaim of an unchanged selection, owner/seat change, empty/absent offer, self-paste, slow
  trickle, oversized offer, cancellation, and UI event-loop responsiveness during a slow transfer.
  A compositor limitation is recorded, not papered over with a control-channel substitute.

- a capture slot completed for the wrong request: no file/reply; a late callback after cancel: no
  reply/panic and released bytes;
- a deliberately duplicated command path under `request_discard`: the one-undo test fails when the
  first-pass guard is removed;
- `resizable_side` with the old exact `Id` or a pre-hashed `IdSalt`: the drag test fails to see the
  resize widget / does not store the width;
- one unnamed input in a scratch kittest harness: `check_accessibility` panics;
- one unsupported glyph: `MissingGlyphPolicy::Panic` panics and `Tofu` does not;
- a hidden `ui.clickWidget` while the widget registry is stale: the request resolves only after a
  fresh layout (test fails if the old geometry is used).

### 7.3 Predeclared acceptance and noise policy

Shared suite thresholds (do not loosen them): investigate a repeatable **>5 % median** or
**>10 % p95** latency regression, **>5 % peak-RSS increase**, any new idle busy loop/repaint, any
missed slider/loupe/export budget, or a visual/document regression. App-specific gates may be
stricter. Apply a documented noise floor: for sub-millisecond values require the relative increase
to exceed 0.05 ms or corroborate with stable instruction/allocation counts. The **stock 0.37
equivalent control** is required in the first report and for every regression decision, so a
0.37-induced change is not attributed to the fork; stock 0.37 remains a control, never a production
stage. Reject noisy comparisons as inconclusive and rerun; **do not widen thresholds** after seeing a
failure. #8731/#8736/#8512 figures are upstream reports, not our measurements; compile duration is
not UI performance.

### API migration

- `egui::Id::new` → `egui::Id::unique` (same hash, so egui state does not reset) and `Ui::id()` →
  `Ui::scope_id()` across the UI crate and tests.
- `WidgetType` → `egui::Role` with the documented variant mapping (`CollapsingHeader` →
  `DisclosureTriangle`, `SelectableLabel` → `Button`, `ComboBox` stays `ComboBox`).
- `Panel` salts: `resizable_side` now passes the original salt to `Panel::left/right`, derives the
  persisted key with `ui.scope_id().with(id)`, and checks the resize drag on that key (the old code
  passed a prebuilt `Id` and would be salted twice). 0.36 exact-`Id` `PanelState` entries for
  `top_bar`, `bottom_bar`, `tool_strip` and `library-problem-banner` are removed once at startup;
  this resets only egui panel memory, never `UiState`, docking JSON, catalog or XMP data.
- `ScrollArea::State.offset` is private: menu arrows store a one-frame `vertical_scroll_offset`
  target, and the right panel reads `clamped_offset()`.
- `Event::MouseWheel` initializers carry `source`; `ui.scroll` accepts optional
  `"source"`, `"unit"` and `"phase"` with the validated values and defaults from §4.9.
- `ComboBox` has the documented lifetime; atoms take `IdSalt` (`Atom::custom`,
  `WidgetAtomResponse::rect`).
- `ViewportCommand::Screenshot` now uses the one-shot callback and `Event::Screenshot`/`UserData`
  are gone. Both headless entry points answer the callback with their painted frame exactly once.
- The fork's `Context::set_language` is fed from `i18n::language()` (the AccessKit root language
  and bidi runs follow the UI locale; command ids and user data stay logical).

### Lifecycle and capture stage (L2b)

- `LightcraftApp` now has a monotonic `AppClock` (`web_time::Instant`, never `i.time` or
  `Date.now` for timing; `now_ms` remains wall-clock only for `library-restored-<ms>` names).
  Headless hosts feed it their simulated time; the first `Headless::step` runs at 0.0.
- `logic` keeps queues, worker polls and time-gated work. Import committing is gated on
  `current_pass_index() == 0` (once per host frame, and once per hidden logic tick), not on the
  clock; all other hidden-relevant timers (Lightroom import, slideshow, auto-import, sidecar retry, screen profile, denoise/faces/focus/model,
  autosave/prefs, toasts, captures) use the app clock.
- `ui` is split into `ui_pass` (first pass only: fresh input, dropped files, external-editor focus,
  shortcuts, perf) and `draw_window` (presentation), then `finish_ui_pass` (completed, nondiscarded
  pass; clears the synthetic in-flight gate). A hidden `run_logic` never reaches it.
- Dropped files are taken once in `raw_input_hook` into an app queue and consumed only in the UI
  phase; web consumes the same queue in `WebApp::ui` (it needs `bytes_async`). Native and web tests
  cover that a hidden logic tick leaves the queue intact.
- `raw_input_hook` injects at most one synthetic batch, refuses to inject before fonts are ready,
  marks the batch in flight until a completed pass consumes it, and keeps a hidden window painting
  with `RequestPaintWhileHidden` while a batch, settlement or queued capture is pending.
- Screenshot capture adopts `craft_ui::capture::CaptureSlot` (CL-2 local tree): four outstanding
  requests, 128 MiB per image, 256 MiB aggregate including completed-not-drained images, admission
  before issue, fresh native viewport geometry, a three-completed-frame/120 ms settle, a forced
  capture at 3 s even while renders are in flight, a 2 s compositor fallback and an 8.12 s
  admission deadline (settle + forced capture + fallback + headless settle). The strong slot stays in the app request
  record; the callback only holds a weak slot and never writes files or touches app state. A
  completion from an older geometry epoch or library generation is retried, never written; an
  image larger than its reservation is rejected; a cancel/timeout/late callback releases its bytes
  with a checked subtraction and replies once.
- Web `Bench::step`, `WebApp` notices/save and the native `PrefsWriter` use the monotonic clock.
  The native menu and window-watch no longer record a hidden pass's stale content rect.

## Review-test repairs — 2026-10-24 (source only)

The managed review-test job `egui037-lightcraft-candidate-20261024-review-tests-13` reported
1155 library passes, 106 failures, 4 ignored, plus 7 of 8 integration tests and the shutdown test
passing. Grouping the failures gave two root causes, repaired here without relaxing a check:

- **Gesture delivery re-checked its own effect.** `reply_delivered_gestures` compared the
  admission-time view/document/dialog/panel snapshot again after the batch had been consumed. Every
  click or key whose purpose is to change that state (opening a dialog, leaving the grid, closing a
  dialog, selecting another photo) was answered with “changed before delivery” although the input
  had done its job. Delivery now requires only that a completed, nondiscarded pass consumed the
  batch. Freshness stays fail-closed twice: at resolution (a later completed layout must match the
  admission snapshot) and in `drop_gestures_stale_before_injection` immediately before a waiting
  gesture's first batch is injected, so a hidden logic tick cannot retarget it; later batches of
  the same gesture may see its own partial effect, and a concurrently queued gesture is checked
  when its events reach the head. A changed snapshot before the fresh layout still cancels, and a
  stale pre-injection batch is cleared and answered with an error.
- **Unlabelled dropdowns.** egui 0.37's `ComboBox::from_id_salt` publishes the selected text as the
  node's value but no accessible name, and kittest 0.37's strict accessibility check rejects it.
  `widgets::name_combo` now gives every dropdown a semantic label (copyright status, keyword set,
  proof profile, denoise limit, smart-album match/field/operator/value, export/contact-sheet/import/
  settings/credits/print dropdowns), so no strict check was disabled.

One lifecycle test assumed the app opened in the photo grid while `UiState` defaults to Detail, so
its “view changed” setup was a no-op; it now changes to PhotoGrid explicitly. New regression tests
cover a delivered gesture that opens a dialog (stays `ok`) and a view change between resolution and
injection (answers once with `canceled` and injects nothing).

No build, test, fmt, clippy, GUI, browser, Windows or performance run was made for this amendment;
the parent runs the managed jobs. The 106 failures and the ComboBox finding are the only failures
inspected in that output; any further finding is reported separately rather than folded in here.
